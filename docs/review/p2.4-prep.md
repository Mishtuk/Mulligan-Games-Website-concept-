**Gaps. Each one needs a DESIGN.md line, or a boss call in DECISIONS, before that part is built:**
- [ ] **G1 (must, designer): staff entry for "Pre-register at the counter" events.** Prereleases, the biggest events,
  use `signup: 'counter'`. 15.7 gives their rows a No-show button, but DESIGN has no way to put a name on the roster
  without checking that person in. Walk-in add (9.2) always checks in and sets "At the door". Spec an "Add a
  pre-registration" action on the roster: name, optional contact, payment (often paid in advance), not checked in.
- [ ] **G2 (decide): players can't cancel or check their own status.** There are no accounts (D5) and no email yet,
  so a player can't cancel. Yet the waitlist reply says "Check this page", and the event page shows only counts.
  Choose one: (a) the success reply gives a personal link (`/signup/<random token>`, never guessable) showing "You're
  in / waitlist #n" with a "Cancel my seat" button, which promotes the next person; or (b) cancelling is staff-only
  ("Can't make it? Call the shop"), and the reply says so. The "auto-promote on cancel" box in PLAN depends on this.
- [ ] **G3 (decide): the duplicate rule.** The prototype refuses a sign-up with the same name (ignoring case and
  spaces), OR email, OR phone. It also matches email and phone as substrings of the stored contact (`c.indexOf(em)`),
  so `am@x.co` counts as a duplicate of `sam@x.com`. Two different "Chris M." can't both sign up. Proposal: compare
  the lower-cased email and the phone digits exactly; a name match alone is a duplicate only for staff walk-ins (the
  screen then offers "Seat anyway").
- [ ] **G4 (decide): registrations when the event changes under them.** Cases: a series edit changes the slot key
  (F3); the sign-up mode changes away from `here` while people are signed up; a series is deleted (`deleteSeries`
  removes the exceptions; what happens to the registrations and their counts for P2.6?); a date is cancelled (keep
  the rows and make the roster read-only, as 15.7 implies; is a date that is brought back live again?). A moved date
  keeps its key (D23), so that case is fine.
- [ ] **G5 (designer): seats lowered below the number already seated** (series edit, or "Change this date" seats).
  Proposal, the same as the prototype: nobody is bumped, the roster reads "30 of 28", and nobody is promoted until the
  count is under the cap again. Raising the seats or removing the cap promotes from the waitlist (prototype test
  below).
- [ ] **G6 (designer): Undo of a cancel when the promoted person has already been checked in.** 15.7 covers this for
  No-show (both keep their seats, "29 of 28"); 9.2's cancel Undo doesn't. The prototype restores a whole-state
  snapshot (`A.undo(before)`), which a server can't do. Undo has to be an inverse operation with a precondition (only
  if the rows are as the action left them), and the spec has to say what happens otherwise.
- [ ] **G7 (designer): what "today" is after midnight.** At 00:30, FNM (7 PM to 1 AM) is still running. Today must open
  on it, not on tomorrow's first event. This is the same root cause as F9.
- [ ] **G8 (designer): the 9.1 shell before P2.5 and P2.6.** The tabs Inventory / Stock / Preorders, the reminder
  chips (low in stock, not reported, preorders arrived) and "Enter results" have nothing behind them yet: hide them
  until their phase. The existing P2.1 site-stats **Dashboard** has no place in 9.1's nav (Today is the default); put
  it under More or as "Website stats".
- [ ] **G9 (designer): the privacy page.** PLAN asks for "privacy page says so"; DESIGN has only the line under the
  form. Spec the URL (`/privacy/`), the footer link and the words: what is kept (name, contact, player ID), for how
  long (N days, plus backups), who sees it (staff; contacts hidden at the counter by default), and that counts stay.
- [ ] **G10 (decide): where the walk-in-only headcount lives in P2.4.** The 9.2 counter is built in P2.4, but its
  number belongs to P2.6 results. Proposal: a per-slot `headcount` row now, which P2.6 reads and lets staff edit.
- [ ] **G11 (designer, small): the no-JS reply page.** 8 says "POST, server reply page" without a layout. Also spec what
  refresh or Back does. Proposal: POST, then a 303 redirect to the event page with the reply shown once, so a reload
  never sends the form again (a second send would hit the duplicate message anyway).
- [ ] **G12 (designer, small): server messages missing from 8.** "That email doesn't look right." and "That phone number
  looks short." exist only in the prototype. Also needed: player ID rules (length, characters) and maximum lengths for
  name and contact.
- [ ] **G13 (decide, small): what a bot sees.** Proposal: a honeypot hit gets the normal "You're in" page and nothing is
  stored (the prototype returns `{ bot: true }` and stores nothing).
- [ ] **G14 (small): "Seat 18 of 28 is yours".** The prototype counts `in + 1`, so after a cancel two people can be told
  the same seat number. Use "You're in. 18 of 28 seats are taken." or keep a seat number that is never reused.

## 2. Rules the server must replicate exactly
From `prototype/js/rules.js` (R) and `mg.js` (MG), unless stated otherwise. Put them in `src/lib/registrations.js`,
pure, with the same names where possible.
- [ ] **Seats.** A seat is a registration with `status: 'in'`. Seats left = `max(0, cap - in)`. With no cap there is no
  limit and never a waitlist (`R.seatsLeft`, `R.isFull`).
- [ ] **Sign-up check order (`R.signUp`):** honeypot (stores nothing) → cutoff → field checks → duplicate → full with
  the waitlist off (refused, `'This one is full. Ask at the counter about open seats.'`) → `in`, or `waitlist` when
  full. **Cutoff uses the server's `cutoffM` (`src/lib/seats.js`), which honours `cutoff: 'before'` +
  `cutoffHours`.** The prototype's `MG.cutoffAt` ignores `cutoff`; don't port it. The closed message is
  `'Sign-ups closed at 7 PM. Walk in if seats are left.'` with the cutoff time.
- [ ] **Last-seat race (`raced`):** the form posts the state the player was shown (`expected`). Shown `in` but
  stored as `waitlist` gives "That seat just went. You're on the waitlist (#1) instead."
- [ ] **One transaction.** Do the sign-up, cancel, promote, No-show, move-in and walk-in steps each inside one SQLite
  transaction (`BEGIN IMMEDIATE`), so two sign-ups for the last seat can't both get `in`.
- [ ] **Waitlist order (`R.waitlistOf`, `R.renumber`):** `waitlistPos` ascending, then `createdAt`, then insert
  order. Renumber 1..n after every change, and set `waitlistPos` to null for everyone not waiting.
- [ ] **Promote (`R.promote`):** while someone is waiting and (there is no cap or `in < cap`), move #1 to `in`. It runs
  after an `in` is cancelled or removed by staff, after a No-show, after a seat increase (series or one-date exception
  `capacity`, `R.afterCapacityChange`) and when the cap is removed. Cancelling a waitlisted person only renumbers.
- [ ] **Over the cap (`R.moveIn`, walk-in "over"):** allowed for staff and returns `over: true`. Nobody is promoted
  until `in < cap` again.
- [ ] **Cancel (`R.cancelReg`):** set `status: 'cancelled'`, `checkedIn: false`, `waitlistPos: null`. A refund is due
  only if the person was `in` and paid `door`, `online` or `credit` (not `comped` or `unpaid`).
- [ ] **Check-in and payment (`R.checkIn`, `R.setPayment`):** only an `in` row can be checked in. Payment is one of
  `unpaid | door | online | comped | credit` (labels `R.PAYMENT_LABEL` / `R.PAYMENT_SHORT`) and can't be set on a
  cancelled row.
- [ ] **Counts (`R.counts`):** in, waitlist, cancelled, noshow, checkedIn (only for `in`), paid (only for `in` with a
  payment other than `unpaid`).
- [ ] **Walk-in (`R.addWalkIn`):** a name is required ("Type a name first."), and a duplicate is caught by name. Mode
  `auto` refuses when full, so the screen can offer the two buttons. Mode `waitlist` adds the person unpaid and not
  checked in. Mode `over` seats them, checked in, with payment `door` (the preset can be changed).
- [ ] **Minimum to run (`R.minToRun`):** below the minimum the event "needs players". This is a warning only and never
  cancels the event.
- [ ] **Card state:** use `seatState(o, nowM, { taken, waiting })` (`src/lib/seats.js`, already the 5.3 order). Feed it
  the counts for that slot on cards, the date page, JSON-LD availability and Today.
- [ ] **Waitlist move (`R.moveWaitlist`):** swap one place up or down, then renumber. Refuse at either end.
- [ ] **Sign-up field checks (`R.validateSignup`):** name required; email or phone required; email shaped `a@b.c`;
  phone at least 7 digits. Messages as in DESIGN 8, plus G12.
- [ ] **Player ID label (`R.playerIdLabel`):** EventLink or Wizards → "Wizards ID (Companion)", Play! Pokemon → "Play!
  Pokemon ID", Bandai → "Bandai TCG+ ID", KONAMI → "KONAMI ID"; any other tool hides the field.
- [ ] **No-show (new; 15.7 only, not in `rules.js`):** set `status: 'noshow'` and `checkedIn: false`, then promote as for
  a cancel. The button shows from `start - arriveByMins` (or from the start), only on `in` rows that aren't checked
  in, and never on walk-in-only or external events. Undo restores the row unless the promoted person was checked in
  meanwhile; then both keep their seats.
- **Don't port:** `R.matches` / `MG.regsFor` treat a registration with no start as matching every slot of that date.
  Key by slot only (D23). The substring duplicate match is G3.
- **Later phases:** `R.unreported` (P2.6) and the stock and preorder rules (P2.5).
